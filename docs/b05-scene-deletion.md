# B05 — удаление сцены: API и Web UI

Задача B05 в product roadmap, milestone P0, интерфейс Web (включая узкий экран браузера). API и действие в редакторе подключены и проверены; Web — done (P0). Статусы нативного Mobile и MCP не меняются.

## API

```http
DELETE /stories/{storyId}/scenes/{sceneId}
Authorization: Bearer <accessToken>
Content-Type: application/json

{ "expectedRevision": 12 }
```

Тело необязательно для совместимости с существующим клиентом. Web UI передаёт `story.revision`, зафиксированный при открытии подтверждения. Если история успела измениться, удаление не выполняется автоматически: нужно перечитать историю и заново подтвердить действие. Неизвестные поля тела отклоняются.

Успех — `200` с полным обновлённым `Story`, включая оставшиеся сцены, `revision + 1` и `status: "draft"`. Ответ не кешируется. Стабильные ID и порядок оставшихся сцен сохраняются, озвучки с привязкой к удалённой сцене исключаются. Можно удалить пустую или единственную сцену; тогда `scenes: []`. Выбор активной сцены принадлежит Web UI, не серверу.

| Ответ | Значение |
| --- | --- |
| `400` | Невалидные UUID или тело запроса. |
| `401` | Нет действующей сессии. |
| `404` | История отсутствует или недоступна этому пользователю; сцена отсутствует (`scene_not_found`). Повторное удаление также возвращает `404`, не меняя ревизию повторно. |
| `409 story_revision_conflict` | Не совпадает `expectedRevision` либо между чтением и сохранением произошло другое изменение. |
| `409 story_not_editable` | История находится в `rendering`, `publishing` или `published`. Удаление разрешено только для `draft` и `ready`. |

Веб-клиент: `deleteScene(token, storyId, sceneId, expectedRevision?) → Promise<Story>`. Контракт также опубликован в генерируемом OpenAPI (`/docs`, `operationId: deleteScene`).

### Согласованность данных

- Проверка ревизии, обновление истории, удаление заданий рендера сцены и постановка файлов в очередь очистки выполняются в одной транзакции. Ошибка откатывает все эти изменения.
- Обычные сохранения истории тоже проверяют ревизию: запрос, прочитавший историю до удаления, не может вернуть удалённую сцену старым JSON-снимком. Это защита записи, а не реализация версионирования артефактов F05.1.
- Постановка рендера проверяет существование сцены под блокировкой истории. Рендер, завершившийся одновременно с удалением, либо попадает в очередь очистки, либо его результат отклоняется существующим worker-механизмом. Удалённая сцена не получает новое задание из запоздавшего запроса.
- Физическая очистка асинхронна и требует работающего worker. Успех API означает сохранённое удаление и надёжно поставленную очистку, а не уже удалённые байты в хранилище.

### Ограничение до F10.1

В текущей модели материалы принадлежат сценам. Сохраняется прежняя семантика: оригиналы, промежуточные файлы, рабочие видео/аудиодорожки и результаты рендера удаляемой сцены ставятся в очередь очистки. Ключи дедуплицируются; материал, который ещё используется другой сценой той же истории, не удаляется.

Это **не медиаархив**: сохранение и повторное использование архивных оригиналов без сцены требует F10.1. Поэтому до реализации F10.1 нельзя обещать «исходники останутся в архиве» или предлагать «Отменить удаление». B05 реализуется раньше F10.1 по явному запросу пользователя; целевые milestones и статус F10.1 не меняются. Подтверждение честно описывает текущую очистку файлов.

## Выбранное размещение

По решению пользователя корзина находится **рядом со скачиванием и `{}` над предпросмотром сцены**, не в заголовке истории и не в дополнительном меню. Одно нажатие открывает подтверждение. Нейтральная иконка становится красной при наведении; разрушительное действие в диалоге выделено красным.

- Общий `ScenePreviewActions` используется в `ScenePreview` на широком экране и в активной карточке `SceneCarousel` на узком.
- Удаление доступно для фото, видео и пустой сцены независимо от доступности скачивания или инспектора.
- На узком экране цели нажатия имеют размер 44×44 px; заголовок и действия переносятся на две строки, а на экране уже 360 px скрывается только подпись формата кадра.
- `SceneDeleteDialog` отвечает за подтверждение; `use-delete-scene` — за снимок подтверждаемой версии, запрос и кеш; `use-story-scene-selection` — за согласование выбора с URL; `scene-deletion-model` — за проверяемые правила восстановления после ошибок и навигации. HTTP остаётся в `api.ts`, страницы и layout-компоненты — композиционными.

## Поведение UI

1. При открытии подтверждения фиксируются ID, отображаемое название и ревизия истории. Диалог «Удалить «Сцена 3»?» предупреждает о файлах и необратимости. Кнопки «Отмена» и «Удалить»; начальный фокус — на отмене, Tab остаётся внутри диалога, Escape закрывает его. Фон редактора становится `inert`.
2. Пока идёт сохранение или загрузка материалов, удаление недоступно. Во время запроса заблокированы повторное подтверждение, закрытие диалога и конкурирующие изменения; показывается «Подождите…». Ошибка не закрывает диалог и не изображает успех.
3. Кеш истории обновляется ответом сервера без отката более новой ревизии; список историй инвалидируется для пересчёта числа сцен. Устаревшие чтения отменяются; смена/размонтирование сцены останавливает существующий опрос скачивания. Оптимистического удаления нет.
4. После удаления активной сцены выбирается следующая в прежнем порядке, если её нет — предыдущая. Другой существующий выбор сохраняется. Нормализация URL использует последний снимок истории с существующей выбранной сценой: обновление кеша до навигации не сбрасывает выбор на первую сцену. После единственной сцены URL очищается до `/stories/{storyId}` и показывается существующий пустой редактор. Завершившийся запрос не возвращает пользователя на старую страницу после выхода из редактора.
5. После ошибки, включая `404` или потерянный ответ, клиент сначала перечитывает историю. Если сцены уже нет, результат согласуется с сервером. При изменённой ревизии нужно закрыть диалог и подтвердить заново. Если чтение тоже не удалось, доступна только «Проверить состояние» — эта кнопка не повторяет DELETE. При неизменённой сцене повторное удаление требует отдельного нажатия.
6. Подписи и сообщения доступны на EN/RU/SR Latin. Фокус после отмены возвращается на кнопку, после исчезновения кнопки — в редактор.

## Проверки

- `yarn build --force && yarn check && yarn test`: типы и 90 регрессионных тестов, в том числе HTTP-контракт и 10 тестов модели удаления/выбора. Принудительная сборка восстанавливает все скомпилированные Web-тесты после Vite build, который очищает общий `apps/web/dist`.
- `STORYTELLER_TEST_DATABASE_URL='<disposable PostgreSQL URL>' yarn test:api:postgres`: 8 интеграционных тестов транзакций, конфликтов, отката очистки и гонок с рендером. Использовать только отдельную тестовую базу: каждый тест создаёт свою временную схему, прогоняет миграции и удаляет только эту схему. Без этой переменной PostgreSQL-тесты пропускаются; рабочий `DATABASE_URL` не используется.
- `node scripts/sync-product-roadmap.mjs --check`: синхронизация product roadmap.
- В браузере проверены расположение кнопки, подтверждение и отмена, Tab/Shift+Tab/Escape и возврат фокуса, узкие экраны 320/390 px.
- После явного разрешения пользователя на отдельном localhost-стенде с временным PostgreSQL проверены фактическое удаление первой, средней, последней и единственной сцены, фото и пустые сцены, сохранение после перезагрузки, выбор соседней сцены, URL, пустой редактор и счётчики библиотеки. Найденная при проверке гонка обновления кеша и URL исправлена и покрыта двумя регрессионными тестами.
- Искусственная задержка подтвердила блокировку повторного действия и закрытия; один клик дал один DELETE. При конфликте ревизии сцена сохранилась до нового подтверждения. После 503 диалог остался открыт; явный повтор завершился успешно. После сбоя DELETE и контрольного GET кнопка «Проверить состояние» выполнила только чтение: счётчик DELETE не увеличился. Рабочие пользовательские данные не использовались.
