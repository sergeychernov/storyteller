# F01.2 — API общего таймлайна

Серверная часть для milestone «Истории на YouTube» в [product roadmap](product-roadmap.md). Готовы чтение таймлайна, перестановка сцен и атомарный перенос материалов. Адаптивный Web подключает перестановку сцен и перенос одного материала между сценами через drag-and-drop. Native Mobile и MCP сохраняют отдельные milestones паритета.

## HTTP

Все операции требуют обычный Bearer token владельца истории. Контракты и ошибки включены в OpenAPI (`/docs`).

| Операция | Метод и путь | Результат |
| --- | --- | --- |
| Прочитать таймлайн | `GET /stories/{storyId}/timeline` | Тайминг сцен, общая длительность и предупреждения; `Cache-Control: private, no-store` |
| Задать порядок сцен | `PUT /stories/{storyId}/scene-order` | Полная обновлённая `Story` |
| Перенести материалы | `POST /stories/{storyId}/scenes/{sceneId}/materials/move` | Полная обновлённая `Story` |

Порядок:

```json
{
  "sceneIds": [
    "00000000-0000-4000-8000-000000000002",
    "00000000-0000-4000-8000-000000000001"
  ],
  "expectedRevision": 12
}
```

`sceneIds` содержит все текущие сцены ровно по одному разу. У пустой истории допустим пустой массив. Монтажный порядок хранится явно в массиве `Story.scenes` в JSONB; `sceneOrder` ответа таймлайна выводится из него. Дублирующей таблицы порядка, сортировки по ID/времени съёмки и миграции не требуется.

Перенос:

```json
{
  "materialIds": ["00000000-0000-4000-8000-000000000010"],
  "targetSceneId": "00000000-0000-4000-8000-000000000002",
  "targetIndex": 0,
  "expectedRevision": 13
}
```

- Исходная и целевая сцены должны различаться и принадлежать истории из URL. Для порядка внутри одной сцены остаётся существующий `PUT …/material-order`.
- `materialIds` — непустой массив без дублей. Все материалы должны находиться в исходной сцене; в целевую они вставляются в порядке запроса.
- `targetIndex` — позиция до операции: 0 означает начало, число материалов целевой сцены — конец. Неверный индекс не исправляется автоматически.
- Перенос сохраняет ID, оригинал, crop/rotation/trim, производное изображение, хеши и аудио/видеодорожки. Ключи файлов не переименовываются, даже если содержат ID прежней сцены. Копирования или задач удаления нет.
- Презентация обеих затронутых сцен сбрасывается по существующим правилам: одиночное фото получает свой renderer/focus/motion, несовместимые макеты снимаются; чужие сцены не меняются. Настроенная длительность сцены сохраняется.
- Опустевшая исходная сцена и её озвучка остаются; удалить её можно отдельно. После удаления исходной сцены перенесённые материалы продолжают принадлежать целевой.

## Конкурентные изменения и версии

Обе новые мутации требуют `expectedRevision`. Разрешены состояния `draft` и `ready`. Успех создаёт одну новую ревизию и переводит историю в `draft`; обновление обеих сцен сохраняется одним compare-and-swap JSONB, поэтому частичного переноса нет.

Проверяется как ревизия клиента, так и ревизия в момент записи. Повтор запроса со старой ревизией возвращает 409, даже если первая попытка успела завершиться. Клиент должен перечитать историю и согласовать намерение; слепой повтор с подставленной новой ревизией недопустим. Даже запрос неизменного порядка с актуальной ревизией создаёт новую ревизию.

Перестановка сохраняет независимые рендеры сцен и привязки озвучки по ID. Перенос меняет входы рендера двух сцен; история версий сохраняется, актуальность пересчитывается механизмом F05.1. Обе операции снимают `music.applied`, сохраняя сам аудиофайл. Полноценные версии мастера, микса и подтверждения подключаются в F04/F07.3/F05.2.

| HTTP | Код / причина |
| --- | --- |
| 400 | Неверная структура, UUID, индекс нецелый/отрицательный, отсутствующая ревизия или лишние поля |
| 401 | Нет действующей сессии |
| 404 | История недоступна; `scene_not_found` или `material_not_found` для отсутствующих участников переноса |
| 409 | `story_revision_conflict` или `story_not_editable` |
| 422 | `invalid_timeline_edit`: неполный/повторяющийся порядок, неизвестный ID в порядке, дубли материалов, та же сцена или индекс за границей |

## Длительность

Каждая запись `scenes` содержит `sceneId`, `index`, `materialIds`, `startSeconds`, `endSeconds`, `durationSeconds` и `durationSource`. Ответ привязан к `storyId` и `revision`.

- Фото и композиции используют настроенную длительность сцены. Это монтажный расчёт, а не подтверждение, что сложный renderer уже реализован или мастер проверен.
- Одиночное видео: конец trim минус начало на исходной временной шкале; без trim — обязательный положительный `sourceDurationSeconds`. Этот же общий расчёт использует подпись длительности в текущем Web.
- Пустая сцена даёт 0 и предупреждение `empty_scene`; её условные пять секунд настройки не изображаются как готовое видео.
- Новая загрузка видео без достоверной длительности отклоняется. Сохранённый file-backed материал без `sourceDurationSeconds` считается некорректным JSON и завершает чтение явной ошибкой схемы: материал не удаляется и длительность не подставляется. Миграция и backfill не нужны, поскольку реальных legacy-записей этого вида нет.
- Межсценовые эффекты ещё не реализованы: текущие стыки без перекрытия, `transitionOverlapSeconds: 0`. API не принимает фиктивные crossfade-параметры. Реальные переходы и учёт фактического перекрытия вынесены в будущую Web-задачу [#505](https://github.com/sergeychernov/storyteller/issues/505), запланированную после Mobile- и MCP-паритета; они не входят в критерии завершения [#19](https://github.com/sergeychernov/storyteller/issues/19).
- Секунды нормализуются до шести знаков после запятой. Покадровая проверка готового мастера относится к F04/F05.2.

В `formatLimits` возвращаются справочные профили длительности YouTube: Shorts, стандартная загрузка и загрузка для подтверждённого аккаунта. Каждый содержит `maxDurationSeconds`, `requiresVerifiedAccount`, `status` (`within_limit` или `exceeded`) и точный `excessSeconds`.

Правила проверены 28.08.2026: [Shorts — до 3 минут](https://support.google.com/youtube/answer/15424877?hl=en); [стандартная загрузка — до 15 минут; подтверждённый аккаунт — до 12 часов либо 256 GB](https://support.google.com/youtube/answer/71673?hl=en). Ровно максимальная длительность допустима.

Это проверка длительности, не разрешение на публикацию: доступность канала, геометрия, размер файла и авторские права здесь не проверяются. Площадка не выбирается и не сохраняется; после выбора площадки в [#42](https://github.com/sergeychernov/storyteller/issues/42) проверка именно выбранного формата подключается в будущей Web-задаче [#504](https://github.com/sergeychernov/storyteller/issues/504), запланированной после Mobile- и MCP-паритета. Предупреждения не блокируют монтаж, не удаляют материалы и не сокращают историю. Новые площадки остаются в следующем product roadmap milestone.

## Web UI

В текущем редакторе реализован вариант A: компактная серверная сводка над лентой сцен и метки на проблемных карточках. Desktop показывает её в левой ленте, мобильный Web — в режиме «Таймлайн». Сводка содержит общую длительность (`MM:SS.xx`, после часа `H:MM:SS.xx`), количество проблем, только превышенные справочные профили YouTube с точным превышением и число пустых сцен. На самой пустой сцене виден текст «Пустая · 0 сек»; информация не передаётся одним цветом или значком.

Тайминг читает отдельный React Query запрос с ключом `profileId + storyId + revision`. После подтверждённой мутации новая ревизия получает отдельный запрос, без клиентского пересчёта и переноса старой сводки как актуальной. Во время запроса виден расчёт; сетевая ошибка оставляет редактор доступным, показывает `role="alert"` и явный повтор.

Сцена меняет позицию локально во время drag, а после отпускания отправляется один `PUT` полного порядка с исходной ревизией. Выбор сцены сохраняется по стабильному ID. Материал из нижней ленты можно перенести на карточку другой сцены: доступные цели подсвечиваются, материал вставляется в конец целевой сцены, и после успешного ответа эта сцена открывается. Drop на исходную сцену не создаёт мутацию. Ошибка откатывает оптимистичное изменение; при `story_revision_conflict` клиент перечитывает историю и явно сообщает о конфликте. Это не реализация нативного Mobile.

Для всех вариантов: сохранять выбор по ID, обновлять UI из возвращённой `Story`, перечитывать тайминг после изменения ревизии; при 409 сохранять намерение пользователя, показывать конфликт и предлагать перечитать актуальное состояние. Перенос видео в композицию может изменить хронометраж и потребовать ещё не готовый renderer; после подтверждения это отражает новый серверный тайминг. Превышение показывается рядом с общей длительностью, без обязательного выбора площадки и без автоматической обрезки.

## Проверка

Регрессии добавлены в существующие domain/API/PostgreSQL suites: перестановка и полнота порядка; перенос, сохранение файлов и версий; авторизация, ошибочные входы, stale revision и гонка при записи; хронометраж и предупреждения; OpenAPI. PostgreSQL проверяет сохранение после нового чтения, удаление опустевшей сцены и конкуренцию перестановки с переносом в изолированной тестовой базе.

Автоматические проверки покрывают точные длительности фото, композиций, исходного и обрезанного видео, пустые сцены и истории, равенство лимиту и превышение. Web-регрессии проверяют сводку, текстовую метку пустой сцены, скрытие успешных лимитов, загрузку, ошибку/retry, смену query key после новой ревизии и подтверждённую аналитику перестановки/переноса без событий на optimistic update, ошибке или `409`. Отдельная регрессия фиксирует контракт drag-safe timeline-видео: `draggable=false`, запрет PiP/remote playback, отсутствие pointer hit testing и обязательную отмену нативного события. Межсценовые эффекты перенесены в #505.

Browser-проверка 01.09.2026 выполнена на desktop 1440×900, 360×800 и viewport Pixel 7 412×915: у rail и summary `scrollWidth === clientWidth`, текст сводки и пустой сцены виден, pointer/touch-oriented drag меняет порядок, error/retry оставляет карточки доступными, console без ошибок. Конфликтный откат и перенос проверены Web-регрессиями. После обнаруженного ранее на физическом Pixel 7 системного long-press меню Chrome у timeline-миниатюр отключены hit testing и нативные действия `<video>/<img>`, а `contextmenu` карточки отменяется. Повторная проверка системного меню на физическом устройстве вынесена в Web release-задачу [#506](https://github.com/sergeychernov/storyteller/issues/506) после отдельно разрешённой публикации и не блокирует #19.

`yarn check`, `yarn test` (194 domain/backend и 56 Web-тестов), `yarn test:story-web` и `yarn build:web` прошли. `yarn test:api:postgres` запущен, но все 22 теста получили `SKIP`: отдельный opt-in `STORYTELLER_TEST_DATABASE_URL` не был задан. Наличие и доступность PostgreSQL по штатному `DATABASE_URL` этим прогоном не проверялись, потому что fixture намеренно не использует runtime-базу без явного разрешения. Поэтому #19 остаётся открытой до реального успешного PostgreSQL-прогона на подтверждённой тестовой базе.
