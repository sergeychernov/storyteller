# Product Roadmap with Milestones — Web / Mobile / MCP

Срез реализации на 28.08.2026: приложение — 54ddbdf; источник функциональности — [hermes-story-skills, 24de17a](https://github.com/sergeychernov/hermes-story-skills/tree/24de17aa9ca376d4b59b4dc27f4866cf787a3c49). Начальные статусы выставлены по коду, без нового запуска приложений.

Цель: развивать создание и публикацию историй в трёх интерфейсах и публичный сайт сервиса. Сценарии 11 скилов служат референсом возможностей, но не определяют обязательный состав MVP: AI-функции вынесены в завершающий milestone с монетизацией. Сохраняем [product-first подход](adr/0001-product-first-foundation.md): общие application/domain/worker, без копирования чатового процесса и legacy-манифестов. Это product roadmap с milestones, задачами и независимыми статусами интерфейсов; [migration-plan.md](migration-plan.md) остаётся архитектурным контекстом.

## Как читать и обновлять roadmap

- ![done](assets/product-roadmap/done.svg) — зелёный фон: задача реализована в указанном интерфейсе в пределах результата, описанного в строке.
- **P0, P1, P2, …, P5, …** — идентификаторы milestones: продуктовых результатов с критериями завершения. В ячейке указан целевой milestone для задачи этого интерфейса, а не степень готовности или уровень важности; номера не ограничены P2.
- **Оранжевый фон** — одна из ближайших 10 незавершённых пар «задача + интерфейс»; текст на плашке остаётся идентификатором целевого milestone. Подсвечивается ячейка статуса, а не вся строка: готовность Web не означает готовность Mobile/MCP.
- **n/a** — задача неприменима к интерфейсу, а не «пока не сделана».
- Столбцы независимы: у одной задачи допустимы Web = done, Mobile = P5, MCP = P4. Завершение общей серверной части не меняет автоматически статусы клиентов.
- Milestones задают порядок развития продукта: сначала Web MVP, затем тот же объём в Mobile, затем в MCP; после этого новые возможности развиваются параллельно. У каждого milestone есть продуктовый результат и критерии завершения; ориентировочные месяцы завершения заданы в блоке `product-roadmap-estimates` и не являются обещанием даты выпуска.
- Частичная реализация сохраняет целевой milestone; остаток фиксируется в последнем столбце. При необходимости разбивать строку на подзадачи, а не помечать всю фичу done.
- ID стабильны: F01–F15 соответствуют прежним 15 пунктам, F16 — публичный сайт, F17 — монетизация AI-функций, суффиксы обозначают подзадачи; B — базовые возможности. При переносе не менять ID. В работе указывать блокер/следующий шаг в примечании, после завершения — свидетельство проверки и только затем done.

Web — [apps/web](../apps/web), включая адаптивный интерфейс на телефоне. Внутренние Web-задачи B14/B15 относятся к запланированному отдельному `apps/admin`, контейнеру и домену `admin.makeitastory.app`, а не к публичному Web-процессу. Mobile — отдельное нативное приложение [apps/mobile](../apps/mobile), не MobileStoryEditor из веба. MCP — [apps/mcp](../apps/mcp): типизированные инструменты, ресурсы и доступ к результатам вместо экранов, но те же операции и правила доступа.

## Milestones и порядок выпуска

MVP — создание и публикация истории без встроенных AI-функций: исходники → ручной монтаж сцен/коллажей и титров → собранная история и просмотр → выбор площадки/формата → подготовка обложки, собственной озвучки и загруженной музыки → проверенный мастер → явное подтверждение → публикация с проверенным результатом. В MVP доступен YouTube; создание и монтаж истории не требуют заранее выбирать площадку. Готовый MP4 или пакет для ручной загрузки не закрывает MVP.


| Milestone | Продуктовый результат           | Критерии завершения                                                                                                                                      |
| --------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0 | MVP на Web | Весь состав YouTube MVP ниже имеет done в Web; история с музыкой, озвучкой и обложкой опубликована в выбранный YouTube-канал и проверена после загрузки. |
| P1 | Mobile догоняет Web MVP | Тот же полный путь, включая звук, обложку и публикацию в YouTube, доступен в нативном приложении; готовый backend переиспользуется. |
| P2 | MCP догоняет MVP | Тот же путь доступен через инструменты/ресурсы, включая авторизацию, проверки, подтверждение публикации и получение её результата. |
| P3 | Параллельное развитие после MVP | Instagram Reels, Telegram Stories, review-доставка, независимый медиаархив F10.1 и редакционный журнал F10.2 — во всех трёх интерфейсах; публичный сайт F16 — в Web. |
| P4 | Монетизация и AI-функции | После P3 доступны платные AI-предложения, генерация музыки и AI-обложки во всех трёх интерфейсах; оплата, доступ, лимиты и учёт затрат проверены до включения платных вызовов. Базовый путь создания и публикации работает без AI. |


Состав MVP: все применимые B, включая язык профиля B12, доступ B13 и внутреннюю админку B14/B15 для Web; F01.2/F01.3; F02–F06; загруженная музыка F07.1 и микс F07.3; YouTube-обложки F08.1.1; F09, F11 и F12; пакет F14.1; выбор площадки после сборки F15.6, подготовка публикации F15.1, YouTube F15.2 и защита от дублей публикации F15.5. Сложные сцены, ручные титры, собственная озвучка, загруженная музыка и обычные обложки остаются в MVP. Медиаархив F10.1, зависящий от него редакционный журнал F10.2, бриф F01.1, генерация музыки F07.2, AI-композит F08.2 и редакционный AI-помощник F13 в MVP не входят. Материалы можно повторно загрузить с устройства; независимое хранение оригиналов после удаления сцены и поиск дублей файлов не требуются для MVP.

После MVP в P3 идут другие площадки: обложки Instagram/Telegram F08.1.2/F08.1.3, review-доставка F14.2 и адаптеры F15.3/F15.4; затем по очереди — медиаархив F10.1 и редакционный журнал F10.2. В P4 — монетизация F17 и встроенные AI-функции F07.2/F08.2/F13 с необязательным брифом F01.1. Платные AI-вызовы не нужны для создания, монтажа или публикации истории в P0–P3.

В milestones P1 и P2 сравнивать с зафиксированным полным объёмом Web MVP: исправления допустимы, расширения запланированы после P2. P1 начинается после готовности Web MVP, P2 — после догоняющего Mobile, параллельное расширение — после паритета MVP.

P3 — первый milestone параллельного развития продукта. P4 — завершающий milestone текущего product roadmap: монетизация и встроенные AI-функции после P3. Новую общую фичу после MVP по умолчанию планировать на один milestone во всех трёх столбцах. Фактическое завершение или перенос отмечать отдельно для каждого интерфейса. Публичный сайт F16 запланирован после MVP, кроме явно запрошенных ранних F16.1/F16.4: они не расширяют объём догоняющих Mobile/MCP, для которых эти страницы имеют n/a. MCP в P2 предоставляет операции редактора внешним клиентам; встроенная AI-генерация сервиса относится к P4.

### Решения по составу продукта — 28–29.08.2026

- **Площадка:** выбирается после сборки и просмотра истории в F15.6. Затем выполняется адаптация под формат и проверка публикации; выбор площадки не входит в бриф и не блокирует монтаж.
- **Длительность:** определяется материалами и фактическим монтажом — длительностями сцен, обрезками и переходами. Поля «желаемая длительность истории» нет. Во время монтажа F01.2/F01.3 показывают хронометраж и превышение максимума доступных площадок/форматов без обязательного выбора цели; после выбора проверяют лимит выбранного формата. Автоматически сокращать историю или удалять материалы нельзя.
- **Язык:** единая настройка профиля B12 для всех историй пользователя, без отдельного выбора в каждой истории. Готовый выбор языка интерфейса B01 не считается реализацией сохранённого языка профиля.
- **Медиаархив:** по решению пользователя F10.1 перенесена из MVP в P3 для Web/Mobile/MCP как улучшение повторного использования материалов. Вместе с ней перенесена зависимая F10.2. В MVP пользователь хранит исходники на своём устройстве и при необходимости загружает их снова; удаление сцены может очищать её серверные файлы по правилам B05, не затрагивая файлы на устройстве. Независимый архив, поиск дублей файлов и редакционный журнал не блокируют MVP. Остальной состав MVP и ранее проверенные done не меняются.
- **Бриф и тон:** F01.1 переносится в P4 как необязательный контекст для F13: смысл истории и пожелания к тону. Это не шаг создания истории в MVP; язык поступает из профиля, площадка и плановая длительность в бриф не входят.
- **AI и монетизация:** F07.2, F08.2 и F13 перенесены в P4 для Web/Mobile/MCP. Включение платных операций зависит от F17. Схему оплаты, тарифы и лимиты определить при реализации; этот перенос не означает готовности функций и не меняет ранее проверенные done.
- **Доступ и внутренняя админка — 29.08.2026:** по запросу пользователя B13/B14/B15 добавлены в P0 и сознательно поставлены перед продолжением F01.2, потому что публичный сайт уже открыт и нужна ранняя наблюдаемость пользователей. [Отдельный план](access-control-admin-plan.md) фиксирует каталог прав, семь ролей, три тестовых тарифа, конфликты overrides, отдельный container/service на `admin.makeitastory.app` и одну API-сессию для основного Web и Admin. B14 сначала даёт read-only мини-админку, B15 — ручные роли, когорты и overrides; платёжный lifecycle и usage остаются F17 в P4. Реализация, DNS и Railway service не создавались.

### Сопровождение

- Источник статуса — ячейка основной таблицы: `Pn`, `n/a` или `done (Pn)`. У завершённой задачи обязательно сохранять её milestone: например, `done (P0)` превращается в `![done](assets/product-roadmap/done.svg "P0")`. На плашке остаётся done, milestone сохраняется в tooltip; это позволяет считать прогресс без потери истории. У оранжевой плашки можно заменить alt-текст на done — синхронизация сохранит milestone из её пути.
- После реализации менять только проверенный интерфейс и записывать результат проверки/остаток в примечании. Частичную задачу не закрывать. Правила обязательны для агента в [AGENTS.md](../AGENTS.md).
- Затем запускать `node scripts/sync-product-roadmap.mjs`: он обновляет фон статусов и этот список, убирает прежнюю оранжевую подсветку и выбирает следующую десятку. Значения статусов он не меняет и готовность по коду не угадывает.
- Перед завершением работы запускать `node scripts/sync-product-roadmap.mjs --check`. Проверка завершается ошибкой при рассинхронизации документа/плашек, неверном статусе, повторяющихся ID или неполной очереди. При добавлении задачи включать её ID ровно один раз в комментарий `product-roadmap-order` выше.



### Данные публичного виджета

- Milestones берутся из таблицы «Milestones и порядок выпуска», короткие подписи EN/RU/SR — из `product-roadmap-public-titles` выше. При добавлении milestone обновлять обе части документа.
- Публичные подписи предназначены потенциальным пользователям и инвесторам: описывать возможности и пользу, не внутренние понятия «паритет» или «догоняющий интерфейс». Технические цели и критерии остаются в основной таблице milestones.
- Прогресс — число done среди применимых пар «задача + интерфейс», назначенных этому milestone; n/a исключается. Это доля закрытых задач, не оценка сроков или трудозатрат. Частичная задача не даёт дробного прогресса.
- Текущая позиция — первый по номеру незавершённый milestone. Пустой milestone не считается выполненным; когда завершены все milestones, показывается отдельное состояние без активного шага.
- Каждая Vite web-сборка читает документ заново и включает только публичные подписи, агрегированные счётчики и идентификатор версии в bundle. Ручной JSON-снимок не хранится; ошибка документа блокирует сборку вместо публикации вымышленных данных. В dev изменения документа обновляют страницу.
- Пересчёт происходит при публикации сайта, а не при публикации истории в YouTube. Уже открытая production-страница получит новую версию после перезагрузки; постоянный опрос не нужен.
- Для деплоя при изменении только документа включить его и генераторы в Railway watch paths: см. [настройку web](deploy-railway.md#web).

Рабочие правила для реализации:

- **Периоды статистики:** сегодня — с 00:00, неделя — с понедельника, месяц — с первого числа, всего — за всё время. Единый пояс статистики — UTC по умолчанию, явно указанный на сайте; не смешивать календарные интервалы со скользящими 7/30 днями.
- **Единица счёта:** подтверждённая публикация с уникальной парой «площадка + внешний ID», датированная фактическим временем публикации, а не запуском рендера. Черновики, экспорты, неуспешные и повторные попытки не учитываются. Кросспостинг на другую площадку — отдельная публикация; подпись счётчика должна говорить о публикациях, не об уникальных историях. Непубличные публикации могут входить только в обезличенную сумму, без ссылок и метаданных.
- **Окно свежести — явное предположение:** фразу «опубликованная не позднее чем 24 часа назад» здесь трактуем как «не старше 24 часов»: время публикации от текущего момента минус 24 часа до текущего момента. Это не выбор историй возрастом от суток и старше.
- **Язык и популярность:** язык посетителя — выбранный язык сайта, при первом визите язык браузера; язык опубликованной истории — сохранённый язык профиля автора B12, зафиксированный в записи публикации F15.1. Отдельного выбора языка истории нет; изменение профиля позднее не переименовывает язык уже опубликованного материала. Начальная метрика популярности — число просмотров YouTube, полученное с площадки, а не просмотры карточки на сайте. При равенстве выше более свежая публикация, затем стабильный ID. Другие площадки требуют отдельного правила сравнения, их сырые просмотры пока не смешивать.
- **Публичность и актуальность:** разрешение на публикацию в YouTube не равно разрешению на витрину сервиса. Private/unlisted, удалённые, недоступные и отозванные автором истории исключаются. Метрики обновляются фоново с учётом доступности и квот API; проверка 24-часового окна действует и на кешированной выдаче. При отсутствии подходящих историй не подставлять старую или иноязычную; при сбое данных не изображать нулевую статистику как достоверную.

## Зависимости и порядок работы

- Для MCP сначала B11 и B02, затем B13; для Mobile — B02 и B03, затем B13. Общие application/domain/worker реализуются при Web MVP, затем подключаются другие интерфейсы; существование backend не означает их готовность.
- Для ранней наблюдаемости открытого продукта действует сознательно изменённый порядок B02 → B13 → B14 → B15 перед продолжением F01.2. B13 задаёт каталог и resolver; B14 разворачивает отдельную read-only админку на общей API-сессии; B15 добавляет только ручные роли, когорты и overrides. Тарифный billing и usage ledger не переносятся из F17 и не блокируют базовый ручной путь продукта.
- Для каждого MVP milestone последовательность реализации: история/загрузка материалов в сцены → сцены/ручные титры/сборка и просмотр → выбор площадки/формата → обложка и собственная озвучка → фиксация визуального таймлайна → загруженная музыка/микс → мастер и QA → подтверждение и публикация в YouTube. Это порядок работы над задачами milestones P0/P1/P2; медиаархив, редакционный журнал и AI-операции не входят в него.
- F01.2 + F05.1 → черновая сборка F04; F01.3 использует её результат. F02/F03/F11/F12 задают сцены; монтаж и ручные титры не зависят от F10.1/F10.2 и F01.1/F13. F01.2/F01.3 показывают фактическую длительность и предупреждения по максимумам доступных форматов уже при монтаже, не требуя заранее выбрать площадку.
- После сборки и просмотра F04/F01.3 выполняется F15.6 — выбор площадки/формата и проверка его лимита; затем платформенная обложка и финальная версия. B02 → B12; язык берётся из профиля, без отдельного шага в истории.
- F06.1 + F06.2 → озвучка сцены; для озвучки группы сначала F12.2. Подготовка и одобрение записи предшествуют финальному миксу.
- F15.6 → F08.1.1 → F09.1: после выбора YouTube готовятся обложка и её длительность в визуальном таймлайне. После фиксации сцен, групп и обложки F07.1 готовит загруженную музыку; F07.3 связывает точный таймлайн с одобренным миксом музыки, озвучки и исходного звука. Генерация F07.2 и AI-композит F08.2 не являются зависимостями MVP.
- F07.3 → финальная сборка F04 → QA F05.2; F05.2 + B12 + выбранная в F15.6 цель → F15.1 → F15.2. F15.5 готова до первой реальной публикации. Пакет F14.1 полезен для выгрузки, но не заменяет работающий YouTube-адаптер.
- F09.2 использует уже фиксированный звук; изменение длительности возвращает историю к подготовке нового таймлайна/микса. Изменение медиа, обложки, метаданных или цели после подтверждения отменяет разрешение на публикацию этой версии.
- После MVP: F08.1.2 + F15.3 — Instagram; F08.1.3 + F09.1 + F15.4 — Telegram Stories; F14.2 — отдельная review-доставка через бота. Эти возможности не блокируют YouTube MVP.
- F10.1 → F10.2 выполняются в P3 после задач других площадок и review-доставки в явной очереди. Архив и журнал не являются зависимостями MVP; до F10.1 действует очистка файлов B05 с возможностью повторной загрузки исходников с устройства.
- F16.1 — оболочка публичного сайта; F16.2 использует подтверждённые записи F15.2/F15.5; F16.3 — язык профиля B12, зафиксированный в публикации F15.1, публикации YouTube, отдельное разрешение на витрину и обновляемые метрики просмотров. F01.1 не является зависимостью публичного сайта. Instagram/Telegram не блокируют запуск сайта. Агрегация и подбор выполняются на сервере; отдельные интерфейсы Mobile/MCP для этих публичных страниц не требуются.
- После P3 в P4: F17 расширяет B13–B15 реальными plan versions, billing lifecycle и идемпотентным usage ledger и только затем разрешает запуск платных F07.2/F08.2/F13. F01.1 хранит необязательный контекст для F13, B12 задаёт язык; F13 использует также таймлайн и контекст материалов. F07.2 использует фиксированный визуальный таймлайн, а его результат передаётся в существующий микс F07.3; применение F08.2 проходит обычное подтверждение обложки и версионирование.
- При планировании milestones учитывать зависимости: при переносе одной задачи проверить затронутые задачи этого интерфейса. После паритета MVP новую общую фичу реализовать на backend один раз и проверить через все три интерфейса.



## Критерии done

- Операция доступна из нужного интерфейса и даёт сохранённый реальный результат. Тип, API без UI, демонстрационная карточка и имитация превью недостаточны.
- Для Web/Mobile проверен пользовательский путь; для MCP — вызов инструмента/ресурса, авторизация, ошибки, статусы асинхронных задач и получение артефакта. Наличие UI не требуется от MCP.
- Пройдены релевантные тесты и ручная проверка результата; для frontend — декомпозиция компонентов/хуков и yarn check. При закрытии строки записать проверку/ссылку на изменение в примечании; остальные столбцы не менять.
- Приёмка B13: deny-by-default resolver детерминированно объединяет plan version, роли, когорты, user overrides, expiry и лимиты, объясняет источники и не заменяет проверку владения ресурсом. Каталог и конфликтные fixtures берутся из [отдельного плана](access-control-admin-plan.md); существующие пользователи не блокируются миграцией. Web, Mobile и MCP проверяются независимо, общий backend не закрывает клиентские статусы.
- Приёмка B14: отдельный container/service реально доступен на `admin.makeitastory.app`, использует общую opaque API-сессию без прямого DB-доступа, raw tokens и второго user store; проверены `401`/`403`, точные CORS origins, CSRF, security headers, `noindex`, audit и read-only метрики без секретов и содержимого историй. Запись домена в документации не считается deployment.
- Приёмка B15: из админки проверены назначения ролей и когорт, allow/deny и limit overrides, start/expiry, обязательная причина, preview effective access, отзыв сессии, audit, конфликты и self-lockout guard. Управление billing products, ценами и usage не считается выполненным до F17.
- Приёмка MVP каждого интерфейса: без брифа, выбора площадки и целевой длительности на старте собрать и просмотреть историю из фото/видео с ручными титрами; хронометраж берётся из монтажа, превышения максимумов доступных форматов видны при редактировании. После сборки выбрать YouTube/формат, при необходимости вручную адаптировать монтаж без потери полной версии; добавить собственную озвучку и загруженную музыку, одобрить микс и обычную обложку, проверить мастер. Язык — из профиля; выбрать канал/аудиторию, подтвердить публикацию и получить проверенный YouTube ID/ссылку. Путь не вызывает платные AI-сервисы. Один экспорт, OAuth или принятый запрос загрузки не считается завершением.
- Дополнительно проверить включённые в MVP сценарии скилов: нестандартный коллаж, группы, наложения, ручные тексты и обычную обложку, локальную замену обложки с сохранением звука. Обработка не изменяет оригиналы; удаление сцены может очищать серверные файлы по правилам B05, без обещания независимого архива. Проверить повторную загрузку исходника с устройства. Правки делают зависимые результаты и разрешение на публикацию устаревшими; повтор публикации после таймаута не создаёт дубль.
- Реальную тестовую публикацию выполнять только после отдельного явного разрешения пользователя с выбранными каналом и видимостью. Для закрытия MVP нужны завершённая обработка YouTube и чтение фактического результата обратно, а не только автоматические тесты.
- Полная межплатформенная приёмка после P3 дополнительно включает Instagram, Telegram Stories, review-доставку, архив/дубли файлов F10.1 и редакционный журнал F10.2. Для архива проверить повторное использование без копий, поиск дублей по хешу и сохранность архивного оригинала после удаления сцены; для журнала — раздельные даты/монтажный порядок и сохранение контекста. Отсутствие этих возможностей не мешает готовности YouTube MVP.
- Приёмка P4: F17 проверен во всех трёх интерфейсах до включения платных AI-вызовов; проверить стоимость/лимиты, отказ, повтор и ошибку провайдера. Контекст F01.1 необязателен; предложения F13, музыка F07.2 и AI-обложка F08.2 доступны с ручным просмотром и подтверждением применения. Базовый монтаж и публикация сохраняют работоспособность без AI.
- Приёмка F16: страницы открываются без входа; счётчики корректны на границах дня/недели/месяца и не удваиваются при retry; витрина учитывает язык, согласие автора, публичность, просмотры и границу 24 часов, включая кеш. Проверены отсутствие кандидатов и сбой источника данных. Готовность сайта оценивается отдельно от YouTube MVP.
- Приёмка F16.4: после изменения статуса новая web-сборка пересчитывает позицию и счётчики; done сохраняет milestone, n/a не входит в знаменатель. Проверены переход между milestones, новые P5+, полностью завершённый roadmap, отсутствие задач и ошибочный документ. Оценки берутся из product-roadmap-estimates, локализуются для EN/RU/SR и обновляются при сборке; отсутствующие даты не выдумываются, ошибочные значения отклоняются. В bundle нет внутренних заметок и исходного Markdown.
- Настройки площадок, максимальная длительность по формату, safe zones и число кадров обложки — версионируемые профили. Проверить значения ниже, ровно на и выше максимума, пересчёт после монтажа/смены цели и предупреждения без автоматического сокращения. Не выдавать правила библиотеки за официальные ограничения; последние перепроверять при реализации адаптеров.
- Отдельные расширения вне обязательного паритета: TikTok, TTS, автоматический ducking и импорт legacy-архивов. Mobile и MCP теперь входят в план. Действующий media-voiceover исключает TTS, несмотря на формулировку README библиотеки.
