# Product Roadmap with Milestones — Web / Mobile / MCP

Срез реализации на 28.08.2026: приложение — 54ddbdf; источник функциональности — [hermes-story-skills, 24de17a](https://github.com/sergeychernov/hermes-story-skills/tree/24de17aa9ca376d4b59b4dc27f4866cf787a3c49). Начальные статусы выставлены по коду, без нового запуска приложений.

Цель: развивать создание и публикацию историй в трёх интерфейсах, публичный сайт сервиса и отдельный Music Clip Studio после основного продукта. Сценарии 11 скилов служат референсом возможностей, но не определяют обязательный состав MVP: личный Codex внутри Storyteller добавляется в P2, специализированные AI-функции и дополнительный тариф с включёнными AI-расходами — в P4, multicamera-клипы — в P5, а разные дубли и отдельно записанные партии — в P6. Сохраняем [product-first подход](adr/0001-product-first-foundation.md): общие application/domain/worker, без копирования чатового процесса и legacy-манифестов. Это product roadmap с milestones, задачами и независимыми статусами интерфейсов; [migration-plan.md](migration-plan.md) остаётся архитектурным контекстом.

## Как читать и обновлять roadmap

- ![done](assets/product-roadmap/done.svg) — зелёный фон: задача реализована в указанном интерфейсе в пределах результата, описанного в строке.
- **P0, P1, P2, …, P5, …** — идентификаторы milestones: продуктовых результатов с критериями завершения. В ячейке указан целевой milestone для задачи этого интерфейса, а не степень готовности или уровень важности; номера не ограничены P2.
- **Оранжевый фон** — одна из ближайших 10 незавершённых пар «задача + интерфейс»; текст на плашке остаётся идентификатором целевого milestone. Подсвечивается ячейка статуса, а не вся строка: готовность Web не означает готовность Mobile/MCP.
- **n/a** — задача неприменима к интерфейсу, а не «пока не сделана».
- Столбцы независимы: у одной задачи допустимы Web = done, Mobile = P5, MCP = P4. Завершение общей серверной части не меняет автоматически статусы клиентов.
- Milestones задают порядок развития продукта: сначала Web MVP, затем тот же объём в Mobile, затем в MCP; после этого новые возможности развиваются параллельно. У каждого milestone есть продуктовый результат и критерии завершения; ориентировочные месяцы завершения заданы в блоке `product-roadmap-estimates` и не являются обещанием даты выпуска.
- Частичная реализация сохраняет целевой milestone; остаток фиксируется в последнем столбце. При необходимости разбивать строку на подзадачи, а не помечать всю фичу done.
- ID стабильны: F01–F15 соответствуют прежним 15 пунктам, F16 — публичный сайт, F17 — дополнительный тариф с включёнными AI-функциями, F18 — multicamera Music Clip Studio, F19 — отдельные дубли и партии, F20 — личный Codex внутри Storyteller, суффиксы обозначают подзадачи; B — базовые возможности. При переносе не менять ID. В работе указывать блокер/следующий шаг в примечании, после завершения — свидетельство проверки и только затем done.

После B16 Web разделён на [apps/site](../apps/site) для публичного сайта, [apps/story-web](../apps/story-web) для Story Studio и [apps/clip-web](../apps/clip-web) для Music Clip Studio на одном origin с разными URL-префиксами; подробности — в [плане frontend-продуктов](frontend-products-and-clip-studio-plan.md) и [ADR 0004](adr/0004-separate-product-frontends.md). Адаптивный Web на телефоне не считается native Mobile. Внутренние Web-задачи B14/B15 относятся к запланированному отдельному `apps/admin`, контейнеру и домену `admin.makeitastory.app`, а не к публичному Web-процессу. Mobile — одно нативное приложение [apps/mobile](../apps/mobile) с независимыми продуктовыми navigation trees, не MobileStoryEditor из веба. MCP — [apps/mcp](../apps/mcp): типизированные инструменты, ресурсы и доступ к результатам вместо экранов, но те же операции и правила доступа.

## Milestones и порядок выпуска

MVP — создание и публикация истории без встроенных AI-функций: исходники → ручной монтаж сцен/коллажей и титров → собранная история и просмотр → выбор площадки/формата → подготовка обложки, собственной озвучки и загруженной музыки → проверенный мастер → явное подтверждение → публикация с проверенным результатом. В MVP доступен YouTube; создание и монтаж истории не требуют заранее выбирать площадку. Готовый MP4 или пакет для ручной загрузки не закрывает MVP.

Состав MVP: все применимые B, включая язык профиля B12, доступ B13, внутреннюю админку B14/B15, раннее разделение frontend-продуктов B16 и продуктовую аналитику B17 для Web; F01.2/F01.3; F02–F06; загруженная музыка F07.1 и микс F07.3; YouTube-обложки F08.1.1; F09, F11 и F12; пакет F14.1; выбор площадки после сборки F15.6, подготовка публикации F15.1, YouTube F15.2 и защита от дублей публикации F15.5. Сложные сцены, ручные титры, собственная озвучка, загруженная музыка и обычные обложки остаются в MVP. Медиаархив F10.1, зависящий от него редакционный журнал F10.2, бриф F01.1, генерация музыки F07.2, AI-композит F08.2 и редакционный AI-помощник F13 в MVP не входят. Материалы можно повторно загрузить с устройства; независимое хранение оригиналов после удаления сцены и поиск дублей файлов не требуются для MVP.

После MVP в начале P3 завершается публичная подача Site и выходит prelaunch-анонс Clip Studio F18.0; затем идут другие площадки: обложки Instagram/Telegram F08.1.2/F08.1.3, review-доставка F14.2 и адаптеры F15.3/F15.4; после них — медиаархив F10.1 и редакционный журнал F10.2. В P4 — монетизация F17 и встроенные AI-функции F07.2/F08.2/F13 с необязательным брифом F01.1. В P5 — Music Clip Studio F18.1–F18.7 для одного одновременно снятого исполнения с нескольких ракурсов. В P6 — F19.1–F19.8 для разных дублей и отдельно записанных музыкантами audio/video партий с независимым звуковым и визуальным монтажом. Оба milestones переиспользуют платформу, но не Story/Scene UI и не требуют AI.

В milestones P1 и P2 сравнивать с зафиксированным полным объёмом Web MVP: исправления допустимы, расширения запланированы после P2. Явные исключения по запросу пользователя — личный Codex F20 внутри Web/native Mobile, MCP-задача F11.1 о декларативном создании layout внешним AI-агентом и независимые задачи F03.3.* для ещё отсутствующих P/L-последовательностей из 2–4 материалов во всех трёх интерфейсах. P1 начинается после готовности Web MVP, P2 — после догоняющего Mobile; внутри P2 сначала закрывается базовый MCP-паритет и F11.1, затем личный Codex F20, после него варианты F03.3.2.*–F03.3.4.*. Пятикарточные варианты F03.3.5.* относятся к P3, шестикарточные F03.3.6.* — к P4.

P3 — первый milestone параллельного развития продукта. P4 добавляет монетизацию и встроенные AI-функции после P3. P5 вводит базовый multicamera Music Clip Studio, P6 расширяет его до разных исполнений и раздельных партий; P6 завершает текущий product roadmap. Новую общую фичу после MVP по умолчанию планировать на один milestone во всех трёх столбцах. Фактическое завершение или перенос отмечать отдельно для каждого интерфейса. Публичный сайт F16 запланирован после MVP, кроме явно запрошенных ранних F16.1/F16.4: они не расширяют объём догоняющих Mobile/MCP, для которых эти страницы имеют n/a. MCP в P2 предоставляет операции редактора внешним клиентам; встроенная AI-генерация сервиса относится к P4, multicamera-операции Clip Studio — к P5, отдельные дубли/партии и многодорожечный микс — к P6.

### Ориентировочные сроки milestones

Основной ориентир оценки обновлён 31.08.2026 при сохранении текущего темпа, последовательной работе над milestones и без расширения команды. Для новых F03.3.* после готовности общего декларативного контракта заложен темп около двух визуально откалиброванных и независимо проверенных layout за рабочий день: группа P2 добавляет примерно 2,5 недели, P3 — 3 недели, P4 — 6 недель. В публичном сниппете месяцы показываются в формате `месяц год` на языке посетителя, с пояснением об ориентировочном характере сроков. Значения в формате `YYYY-MM` хранятся только в блоке ниже и обновляются осознанно; проценты готовности не пересчитывают даты автоматически. Если для нового milestone оценки ещё нет, дата не показывается. Эти ориентиры не меняют порядок выпуска, состав milestones или статусы задач.

### Решения по составу продукта — 28–29.08.2026

- **Площадка:** выбирается после сборки и просмотра истории в F15.6. Затем выполняется адаптация под формат и проверка публикации; выбор площадки не входит в бриф и не блокирует монтаж.
- **Длительность:** определяется материалами и фактическим монтажом — длительностями сцен, обрезками и переходами. Поля «желаемая длительность истории» нет. Во время монтажа F01.2/F01.3 показывают хронометраж и превышение максимума доступных площадок/форматов без обязательного выбора цели; после выбора проверяют лимит выбранного формата. Автоматически сокращать историю или удалять материалы нельзя.
- **Язык:** единая настройка профиля B12 для всех историй пользователя, без отдельного выбора в каждой истории. Готовый выбор языка интерфейса B01 не считается реализацией сохранённого языка профиля.
- **Медиаархив:** по решению пользователя F10.1 перенесена из MVP в P3 для Web/Mobile/MCP как улучшение повторного использования материалов. Вместе с ней перенесена зависимая F10.2. В MVP пользователь хранит исходники на своём устройстве и при необходимости загружает их снова; удаление сцены может очищать её серверные файлы по правилам B05, не затрагивая файлы на устройстве. Независимый архив, поиск дублей файлов и редакционный журнал не блокируют MVP. Остальной состав MVP и ранее проверенные done не меняются.
- **Бриф и тон:** F01.1 переносится в P4 как необязательный контекст для F13: смысл истории и пожелания к тону. Это не шаг создания истории в MVP; язык поступает из профиля, площадка и плановая длительность в бриф не входят.
- **Личный Codex и дополнительный AI-тариф — 31.08.2026:** по запросу пользователя F20 добавлена в P2 для Web/native Mobile как встроенный интерфейс персонального агента с managed ChatGPT/Codex-авторизацией и расходованием лимитов самого пользователя; публичный MCP остаётся отдельной задачей и для F20 имеет `n/a`. Специализированные F07.2/F08.2/F13 остаются в P4 и доступны по явному выбору источника: личный Codex F20 либо переименованная F17 — дополнительный тариф Storyteller с включёнными AI-расходами, billing lifecycle и usage ledger. Автоматически переключать пользователя с личного источника на оплачиваемый сервисом нельзя. Сроки milestones этим решением пока не пересчитаны: до изменения ориентиров нужна отдельная техническая оценка изолированного agent runtime, хранения auth-состояния и Web/native Mobile UX.
- **AI и монетизация:** F07.2, F08.2 и F13 перенесены в P4 для Web/Mobile/MCP. Включение оплачиваемых Storyteller операций зависит от F17; личный Codex F20 не переносит специализированные AI-функции из P4 в P2. Провайдера, цену дополнительного тарифа и реальные лимиты определить при реализации; этот перенос не означает готовности функций и не меняет ранее проверенные done.
- **Декларативные layout через внешний AI-агент — 30.08.2026:** по запросу пользователя в P2 добавлена MCP-задача F11.1. Она позволяет внешнему AI-клиенту описать layout данными и не включает встроенный AI-вызов Storyteller, оплату или генерацию исполняемого кода. Сохранение требует явного подтверждения, прохождения общей схемы/валидатора и проверки preview/render parity; Web и native Mobile не получают отдельного интерфейса этой операции.
- **Полный набор последовательностей animated-collage — 31.08.2026:** по запросу пользователя добавлены 116 независимых задач F03.3.* — ровно по одной для каждой ещё отсутствующей P/L-последовательности из 2–6 материалов. Восемь уже реализованных последовательностей не дублируются. 24 задачи длины 2–4 относятся к P2, 30 пятикарточных — к P3, 62 шестикарточных — к P4. У каждой задачи собственный layout definition, validator и render-геометрия; общий редактор и compositor можно переиспользовать. Статусы Web, native Mobile и MCP проверяются отдельно. При текущем ориентире около двух принятых layout за рабочий день оценки пересчитаны: P2 — декабрь 2026, P3 — февраль 2027, P4 — май 2027; последовательные P5/P6 сдвинуты на июль и октябрь 2027.

### Сопровождение

- Источник статуса — ячейка основной таблицы: `Pn`, `n/a` или `done (Pn)`. У завершённой задачи обязательно сохранять её milestone: например, `done (P0)` превращается в `![done](assets/product-roadmap/done.svg "P0")`. На плашке остаётся done, milestone сохраняется в tooltip; это позволяет считать прогресс без потери истории. У оранжевой плашки можно заменить alt-текст на done — синхронизация сохранит milestone из её пути.
- После реализации менять только проверенный интерфейс и записывать результат проверки/остаток в примечании. Частичную задачу не закрывать. Правила обязательны для агента в [AGENTS.md](../AGENTS.md).
- Затем запускать `node scripts/sync-product-roadmap.mjs`: он обновляет фон статусов и этот список, убирает прежнюю оранжевую подсветку и выбирает следующую десятку. Значения статусов он не меняет и готовность по коду не угадывает.
- Перед завершением работы запускать `node scripts/sync-product-roadmap.mjs --check`. Проверка завершается ошибкой при рассинхронизации документа/плашек, неверном статусе, повторяющихся ID или неполной очереди. При добавлении задачи включать её ID ровно один раз в комментарий `product-roadmap-order` выше.



### Данные публичного виджета

- Milestones берутся из таблицы «Milestones и порядок выпуска», короткие подписи EN/RU/SR/ES — из `product-roadmap-public-titles` выше. При добавлении milestone обновлять обе части документа.
- Публичные подписи предназначены потенциальным пользователям и инвесторам: описывать возможности и пользу, не внутренние понятия «паритет» или «догоняющий интерфейс». Технические цели и критерии остаются в основной таблице milestones.
- Прогресс milestone — число done среди применимых пар «задача + интерфейс», назначенных этому milestone; общий прогресс product roadmap — та же доля по всем milestones. Оба процента пересчитываются при каждой сборке, n/a исключается. Это доля закрытых задач, не оценка сроков или трудозатрат. Частичная задача не даёт дробного прогресса.
- Текущая позиция — первый по номеру незавершённый milestone. Пустой milestone не считается выполненным; когда завершены все milestones, показывается отдельное состояние без активного шага.
- Каждая Vite web-сборка читает документ заново и включает только публичные подписи, агрегированные счётчики и идентификатор версии в bundle. Ручной JSON-снимок не хранится; ошибка документа блокирует сборку вместо публикации вымышленных данных. В dev изменения документа обновляют страницу.
- Пересчёт происходит при публикации сайта, а не при публикации истории в YouTube. Уже открытая production-страница получит новую версию после перезагрузки; постоянный опрос не нужен.
- Для деплоя при изменении только документа включить его и генераторы в Railway watch paths: см. [настройку web](deploy-railway.md#web).

Для рядов из двух или трёх карточек редактор показывает только четыре иконки расположения: `ascending`, `level`, `descending` и `random` (беспорядочное доступно для многострочных layout), по умолчанию используется `ascending`; технические пределы смещения в UI не раскрываются. При явном выборе иконки, ручном выборе layout и добавлении, удалении либо перестановке материалов сервер заново рассчитывает скрытый `cardOffsets[{ materialId, offsetY }]`: соседняя случайная разница для наклонных режимов остаётся в пределах 20–40 px выходного кадра, ровный режим сохраняет нули, а одиночные ряды не смещаются. Несвязанные правки рамки и тайминга сохраняют рассчитанные значения. Углы не выводятся в редактор, но сохраняются по `materialId`, возвращаются в JSON, входят в render fingerprint и одинаково применяются Web-preview и FFmpeg; старые сцены получают воспроизводимые углы при чтении. По умолчанию выбирается затемнённый lossless последний кадр предыдущей сцены; до его готовности Web и FFmpeg используют первый кадр первой карточки с тем же crop/rotation/trim и тем же фиксированным затемнением. Настройки затемнения отсутствуют: предыдущий кадр всегда затемнён, пользовательский ресурс всегда показывается без затемнения. Пользовательское видео проигрывается один раз и удерживает последний кадр и в Web-preview, и в FFmpeg; оно не становится карточкой. Старое `background.mode=first-material` при чтении мигрирует первый материал в отдельный resource без потери файла, а дальнейшие изменения рамки, длительности и layout не пересылают и не сбрасывают фон. ### Недостающие последовательности animated-collage

В обозначениях ниже `P` — portrait, `L` — landscape после применения rotation и crop. Каждая строка — независимая задача для одной точной последовательности из 2–6 материалов. Общие критерии каждой задачи: отдельный декларативный layout definition и validator количества, форматов и последовательности; собственные конечная геометрия, время остановки, `stackOrder` и фиксированное перекрытие; подходящий редактор может переиспользоваться несколькими layout. Изображения и видео принимаются без различий, а Storybook, Web-preview и FFmpeg-render должны совпадать. Web, native Mobile и MCP проверяются независимо; пакетная реализация нескольких definitions не закрывает непроверенные строки.

Реализованные в F03.1 последовательности сюда не дублируются: `LL`, `PPL`, `PPPP`, `PPLL`, `PPLPP`, `PPPPL`, `PPPPLL`, `PPPPPP`.

Рабочие правила для реализации:

- **Периоды статистики:** сегодня — с 00:00, неделя — с понедельника, месяц — с первого числа, всего — за всё время. Единый пояс статистики — UTC по умолчанию, явно указанный на сайте; не смешивать календарные интервалы со скользящими 7/30 днями.
- **Единица счёта:** подтверждённая публикация с уникальной парой «площадка + внешний ID», датированная фактическим временем публикации, а не запуском рендера. Черновики, экспорты, неуспешные и повторные попытки не учитываются. Кросспостинг на другую площадку — отдельная публикация; подпись счётчика должна говорить о публикациях, не об уникальных историях. Непубличные публикации могут входить только в обезличенную сумму, без ссылок и метаданных.
- **Окно свежести — явное предположение:** фразу «опубликованная не позднее чем 24 часа назад» здесь трактуем как «не старше 24 часов»: время публикации от текущего момента минус 24 часа до текущего момента. Это не выбор историй возрастом от суток и старше.
- **Язык и популярность:** язык посетителя — выбранный язык сайта, при первом визите язык браузера; язык опубликованной истории — сохранённый язык профиля автора B12, зафиксированный в записи публикации F15.1. Отдельного выбора языка истории нет; изменение профиля позднее не переименовывает язык уже опубликованного материала. Начальная метрика популярности — число просмотров YouTube, полученное с площадки, а не просмотры карточки на сайте. При равенстве выше более свежая публикация, затем стабильный ID. Другие площадки требуют отдельного правила сравнения, их сырые просмотры пока не смешивать.
- **Публичность и актуальность:** разрешение на публикацию в YouTube не равно разрешению на витрину сервиса. Private/unlisted, удалённые, недоступные и отозванные автором истории исключаются. Метрики обновляются фоново с учётом доступности и квот API; проверка 24-часового окна действует и на кешированной выдаче. При отсутствии подходящих историй не подставлять старую или иноязычную; при сбое данных не изображать нулевую статистику как достоверную.

## Зависимости и порядок работы

- Для MCP сначала B11 и B02, затем B13; для Mobile — B02 и B03, затем B13. Общие application/domain/worker реализуются при Web MVP, затем подключаются другие интерфейсы; существование backend не означает их готовность.
- Для раннего разделения продуктов и наблюдаемости действует сознательно изменённый порядок B02 → B16 → B17 → B13 → B14 → B15 перед продолжением F01.2. B16 переносит публичный Site и Story Studio в независимые workspaces, создаёт только boundary Clip Web и сохраняет текущий продукт; B17 измеряет безопасные outcome-события в выбранной внешней аналитике, но не заменяет административные данные; B13 задаёт каталог и resolver; B14 разворачивает отдельную read-only админку на общей API-сессии; B15 добавляет только ручные роли, когорты и overrides. Тарифный billing и usage ledger не переносятся из F17 и не блокируют базовый ручной путь продукта.
- Для каждого MVP milestone последовательность реализации: история/загрузка материалов в сцены → сцены/ручные титры/сборка и просмотр → выбор площадки/формата → обложка и собственная озвучка → фиксация визуального таймлайна → загруженная музыка/микс → мастер и QA → подтверждение и публикация в YouTube. Это порядок работы над задачами milestones P0/P1/P2; медиаархив, редакционный журнал и специализированные AI-операции F07.2/F08.2/F13 не входят в него. F11.1 выполняется в P2 как отдельная операция внешнего AI-агента после появления общего декларативного layout-контракта F03/F11 и MCP-доступа B11/B13. После базового MCP-паритета и F11.1 выполняется встроенный личный Codex F20 для Web/native Mobile: он использует отдельный изолированный agent runtime и внутреннюю application boundary, а не публичный MCP. Затем выполняются F03.3.2.*–F03.3.4.*; F03.3.5.* выполняются в P3, F03.3.6.* — в P4. Каждая строка layout добавляет ровно одну последовательность, зависит от общего контракта F03.1/F03.2 и закрывается только после независимой проверки Web, native Mobile и MCP.

Проверить значения ниже, ровно на и выше максимума, пересчёт после монтажа/смены цели и предупреждения без автоматического сокращения. Не выдавать правила библиотеки за официальные ограничения; последние перепроверять при реализации адаптеров.
- Отдельные расширения вне обязательного паритета: TikTok, TTS, автоматический ducking и импорт legacy-архивов. Mobile и MCP теперь входят в план. Действующий media-voiceover исключает TTS, несмотря на формулировку README библиотеки.
