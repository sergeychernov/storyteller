# F05.1 — версии результатов и зависимости

## Результат для Web MVP

В milestone P0 каждый поддерживаемый экспорт сцены хранит снимок входов, параметры,
SHA-256 содержимого и состояние обработки. Для каждого независимо скачиваемого
результата сцены (`video`, `audio`, `combined`) сохраняется только последнее
запрошенное состояние. Служебный lossless-кадр имеет отдельный слот хранения и не
вытесняется запросом пользовательского экспорта.

Активная версия показывает сохраняемый сервером прогресс: ожидание worker без
вымышленного процента, загрузку исходников, фактический процент FFmpeg по
обработанному времени, финализацию и сохранение результата. Поэтому закрытие или
перезагрузка окна не сбрасывает индикатор и не запускает отдельный локальный таймер.

Правка сцены делает последний результат устаревшим сразу при следующей проверке API,
без обязательного запуска нового рендера. Запрос нового результата атомарно удаляет
предыдущую строку того же слота и ставит её готовый файл в надёжную очередь очистки.
Незатронутые сцены, исходники, производные материалы, служебные кадры и независимые
режимы экспорта при этом сохраняются. Точный возврат к прежним входам создаёт новый
запрос: полная история финальных MP4/M4A намеренно не используется как кеш.

## Контракт

- У оригинала, обработанного изображения, видеодорожки и аудиодорожки сохраняется
  `contentHash`: SHA-256 реальных байтов. Имена файлов, пути и ETag не заменяют хеш.
  Хеширование потоковое. Исходники остаются неизменными при редактировании.
- `scene_renders.input` содержит неизменяемый снимок рецепта и `dependencies`:
  роли, хеши, параметры обработки и связи `parents`. Сейчас поддержаны цепочки
  оригинал → обработанное фото → видео сцены и оригинал → отдельные дорожки →
  выбранный экспорт. При повторной попытке допустимо обновить расположение
  тех же входных байтов; версия при этом не меняется.
- [Производный кадр сцены](scene-frames.md) хранится отдельным lossless PNG с
  собственными `inputHash` и SHA-256. Политика `base-visual` исключает титры и
  поверхностные слои. Роль зависимости `scene-frame` переносит хеш PNG и версию
  исходной сцены в fingerprint зависимых сцен и будущих коллажей.
- `inputHash` вычисляется из канонических параметров и всей цепочки зависимостей.
  Он включает версию рендера, но не общую ревизию истории и не расположение файлов.
  Аудиоэкспорт не зависит от crop, rotation и анимации; временной trim влияет на
  все режимы. Видео без звука не зависит от обработанной аудиодорожки.
- `status` (`queued/running/ready/failed/canceled`) описывает обработку;
  `current` отдельно сообщает соответствие текущему монтажу. Последний результат
  может стать устаревшим после правки, но никогда не выдаётся как текущий файл.
- `progressPercent` хранит целое значение `0…100`, а `progressPhase` — один из
  `queued/downloading/rendering/finalizing/uploading/ready`. Worker обновляет их
  только при активной lease; чужой или завершивший попытку worker не может менять
  прогресс. `ready` всегда нормализуется в `100/ready`, включая результат старого
  worker во время поэтапного локального обновления.
- `GET /stories/:storyId/scenes/:sceneId/renders` возвращает не более одного
  последнего результата на каждый режим экспорта. Ответ включает `inputHash`,
  `contentHash` готового файла, дату, параметры, зависимости, режим, статус и
  актуальность. Список, одиночный статус и файл
  доступны только владельцу существующей истории и сцены, с `private, no-store`.
- `/renders/:renderId/content` перепроверяет актуальность и отвечает
  `409 scene_render_stale` для старой версии. Web не сохраняет обходящий эту
  проверку постоянный Blob URL; каждое скачивание снова обращается к API.
- Постановка в очередь проверяет ревизию под блокировкой строки истории.
  Изменение между чтением снимка и enqueue даёт `409 story_revision_conflict`,
  удаление сцены — 404. Поздний результат старого снимка не становится актуальным.
- Worker проверяет хеши фактически читаемых входов и сохраняет хеш готового файла.
  У каждой попытки собственный ключ результата: очистка проигравшей попытки
  не удаляет результат другого worker. Завершение принимает только владелец
  активной задачи.

## Debug JSON сцены

Окно `{}` сохраняет прежние поля сцены и добавляет `renderResults` на верхнем
уровне JSON. Массив содержит только последние результаты
независимых режимов, а не историю. Каждый результат содержит полные `inputHash`, `contentHash` готового
результата, `dependencies` с хешами входов, параметры, дату, `status`, `current`,
`progressPercent` и `progressPhase`.
Данные берутся из того же авторизованного API и кеша, что и текущие результаты скачивания.
Старые материалы не переписываются: вычисленные для них хеши видны в зависимостях
сохранённой версии, а не обязательно в `materials[].contentHash`.

Запрос обновляется каждые 800 мс при активной версии и раз в две секунды в покое,
пока содержимое окна
смонтировано. После закрытия debug-окна его подписка и запросы прекращаются.
У сцены без результатов отображается `renderResults: []`; при загрузке
или ошибке — `renderResults: null` и отдельное сообщение EN/RU/SR/ES. Ошибка
повторной загрузки не выдаёт старые данные за успешно обновлённые.

Технические данные последнего результата остаются в debug JSON, но из обычного окна
скачивания удалены список, хеши и пометка «устарела». Пользователь видит выбранный
формат, фактический прогресс и готовую ссылку без дублирующей истории.

## Совместимость и выпуск

Миграция 4 обратно совместима со схемой 3: добавляет nullable
`scene_renders.content_hash`, сохраняет старые строки с `NULL` и допускает прежние
SQL-запросы API/worker. Существующие истории не переписываются; при откате кода
колонку удалять не нужно. `ALTER TABLE` требует блокировку, поэтому отсутствие
изменения данных не означает отсутствия времени ожидания. У старых материалов
без хешей байты читаются при построении версии, и их хеши сохраняются в снимке
рендера. Старые задания без цепочки
зависимостей не признаются актуальными: первый запрос создаёт проверяемую версию.
Ошибка чтения старого материала возвращается явно, без вымышленного хеша.

Миграция 8 добавляет к `scene_renders` обязательные процент и этап с безопасными
значениями по умолчанию. Существующие готовые версии переводятся в `100/ready`,
активные — в начало загрузки исходников, остальные — в `0/queued`; старые INSERT
остаются валидными.

Миграция 9 добавляет вычисляемый `render_slot`, сохраняющий совместимость со старыми
INSERT, оставляет последнюю строку для каждого сочетания сцены и слота, а файлы
удалённых строк помещает в `object_deletion_jobs`. Новая постановка в очередь
выполняет ту же замену и планирование очистки одним SQL-выражением. Удаление старого
активного задания лишает его lease; если прежний worker уже успел загрузить файл,
его существующая защита позднего завершения также ставит этот файл на удаление.

CI проверяет миграцию на отдельной PostgreSQL: новая база, параллельный/повторный
запуск, обновление со схемы 3, записи старого формата и откат при ошибке. Команда
`yarn db:migrate` использует собранный Node.js runner и только `DATABASE_URL`, без
API-ключей. В CD она запускается перед API и worker; ошибка останавливает выпуск
сервиса. Подробности и настройки — в [руководстве CI/CD](deploy-railway.md#database-migrations-in-cicd).

Первый выпуск F05.1 требует порядка: миграция в pre-deploy worker → обновление
всех worker и остановка старых экземпляров → API → Web. Нельзя оставлять старые
worker обрабатывать задания нового API: они не сохраняют хеш результата.
Pre-deploy не задаёт порядок между сервисами автоматически. 28 августа 2026 года
первый выпуск в production выполнен именно в этом порядке: проверенный в CI коммит
`dc4871a62aee305f0ee7e64de7e59f067270e79d` отдельно развёрнут в worker, API и Web;
старые экземпляры worker остановлены до запуска нового API. Результаты и идентификаторы
выпуска записаны в [руководстве CI/CD](deploy-railway.md#verified-first-rollout-2026-08-28).

Для каждого режима экспорта и служебного кадра сохраняется только последний запрос.
Финальные файлы вытесненных запросов удаляются асинхронно. Политика хранения
исходников и промежуточных материалов остаётся зависимой от их собственной цепочки,
а архивные оригиналы относятся к F10.1; F05.1 не добавляет undo или восстановление удалённых материалов.
Объектные ключи внутри приложения неизменяемы: замена содержимого создаёт новый
объект, а не перезаписывает старый путь.

## Связанные задачи product roadmap

F04 добавит мастер истории и его зависимости от версий сцен. F07.3 добавит микс,
привязанный к точному таймлайну. Проверка качества и подтверждения относятся к
F05.2/F08.1.1/F15.1, а не к статусу `current`. Эти возможности не объявлены
реализованными. Native Mobile и MCP сохраняют milestones P1/P2.

## Проверка

Итог текущей локальной проверки: 182 Node-теста, 46 Web-тестов и 18 PostgreSQL-тестов прошли. Для повторной проверки:
`yarn check`, `yarn test`, а для отдельной временной базы —
`STORYTELLER_TEST_DATABASE_URL=... yarn test:api:postgres`.
Также прошли `yarn check --force`, 22 тогдашних теста `yarn test:roadmap`,
проверка согласованности прежнего Markdown-roadmap и production-сборка Web.

- Тесты продукта: исходные и производные хеши, локальное устаревание,
  независимость аудио от визуальных правок, влияние trim, неизменность другой сцены,
  замена финального результата без удаления независимых слотов, старые материалы, запрет чужого доступа, удаление сцены,
  отказ при несовпадении байтов, изоляция файлов конкурирующих попыток и остановка
  Web polling при устаревании.
- PostgreSQL: сохранение хеша и даты после повторного открытия репозитория,
  защита по ревизии, повторная попытка с новым расположением входа,
  отказ чужому/завершившему работу worker, регрессии гонок удаления и совместимость
  миграции 4. Проверен production runner без API-ключа; ошибка после DDL откатывает
  и схему, и запись версии, а повторный запуск успешно завершает миграцию.
- Команды CI выполнены локально на временной базе и в
  [GitHub Actions #33204145109](https://github.com/sergeychernov/storyteller/actions/runs/33204145109):
  два `yarn db:migrate` без API-ключа, затем `/health` для dev и compiled API.
  Проверки совместимости миграции, 98 тестов продукта, 13 PostgreSQL-тестов,
  22 теста product roadmap и сборки Web/Mobile завершились успешно.
- На изолированном локальном стенде через Web выполнены реальный рендер,
  изменение анимации, отклонение старого скачивания и создание нового результата. Скачанный H.264 MP4:
  1080×1920, 30 FPS, 5 секунд; SHA-256 совпадает с сохранённым значением.
- В браузере проверены ширины 1280/390/320 px, включая раскрытые параметры и
  длинные хеши: горизонтального переполнения нет, ошибок в консоли нет.
