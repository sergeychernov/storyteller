# F05.1 — версии результатов и зависимости

## Результат для Web MVP

В milestone P0 каждый поддерживаемый экспорт сцены хранит снимок входов, параметры,
SHA-256 содержимого и состояние обработки. В окне «Скачать сцену» видны сохранённые
версии, их актуальность и данные сборки. История версий доступна и после изменения
состава сцены на пока неподдерживаемый для экспорта.

Правка сцены делает зависимые версии устаревшими сразу при следующей проверке API,
без обязательного запуска нового рендера. Незатронутые сцены и независимые режимы
экспорта переиспользуют готовый результат. Точный возврат к прежним входам и
параметрам возвращает ту же версию с тем же ID, без нового рендера.

## Контракт

- У оригинала, обработанного изображения, видеодорожки и аудиодорожки сохраняется
  `contentHash`: SHA-256 реальных байтов. Имена файлов, пути и ETag не заменяют хеш.
  Хеширование потоковое. Исходники остаются неизменными при редактировании.
- `scene_renders.input` содержит неизменяемый снимок рецепта и `dependencies`:
  роли, хеши, параметры обработки и связи `parents`. Сейчас поддержаны цепочки
  оригинал → обработанное фото → видео сцены и оригинал → отдельные дорожки →
  выбранный экспорт. При повторной попытке допустимо обновить расположение
  тех же входных байтов; версия при этом не меняется.
- [Производный кадр сцены](scene-frames.md) хранится отдельным lossless PNG с
  собственными `inputHash` и SHA-256. Политика `base-visual` исключает титры и
  поверхностные слои. Роль зависимости `scene-frame` переносит хеш PNG и версию
  исходной сцены в fingerprint зависимых сцен и будущих коллажей.
- `inputHash` вычисляется из канонических параметров и всей цепочки зависимостей.
  Он включает версию рендера, но не общую ревизию истории и не расположение файлов.
  Аудиоэкспорт не зависит от crop, rotation и анимации; временной trim влияет на
  все режимы. Видео без звука не зависит от обработанной аудиодорожки.
- `status` (`queued/running/ready/failed/canceled`) описывает обработку;
  `current` отдельно сообщает соответствие текущему монтажу. Готовая устаревшая
  версия остаётся в истории, но не выдаётся как текущий файл.
- `GET /stories/:storyId/scenes/:sceneId/renders` возвращает версии от новых к старым.
  Ответ включает `inputHash`, `contentHash` готового файла, дату, параметры,
  зависимости, режим, статус и актуальность. Список, одиночный статус и файл
  доступны только владельцу существующей истории и сцены, с `private, no-store`.
- `/renders/:renderId/content` перепроверяет актуальность и отвечает
  `409 scene_render_stale` для старой версии. Web не сохраняет обходящий эту
  проверку постоянный Blob URL; каждое скачивание снова обращается к API.
- Постановка в очередь проверяет ревизию под блокировкой строки истории.
  Изменение между чтением снимка и enqueue даёт `409 story_revision_conflict`,
  удаление сцены — 404. Поздний результат старого снимка не становится актуальным.
- Worker проверяет хеши фактически читаемых входов и сохраняет хеш готового файла.
  У каждой попытки собственный ключ результата: очистка проигравшей попытки
  не удаляет результат другого worker. Завершение принимает только владелец
  активной задачи.

## Debug JSON сцены

Окно `{}` сохраняет прежние поля сцены и добавляет `renderVersions` на верхнем
уровне JSON. Каждая версия содержит полные `inputHash`, `contentHash` готового
результата, `dependencies` с хешами входов, параметры, дату, `status` и `current`.
Данные берутся из того же авторизованного API и кеша, что и история скачиваний.
Старые материалы не переписываются: вычисленные для них хеши видны в зависимостях
сохранённой версии, а не обязательно в `materials[].contentHash`.

Запрос и обновление раз в две секунды работают только пока содержимое окна
смонтировано. После закрытия debug-окна его подписка и запросы прекращаются.
У сцены без сохранённых версий отображается `renderVersions: []`; при загрузке
или ошибке — `renderVersions: null` и отдельное сообщение EN/RU/SR/ES. Ошибка
повторной загрузки не выдаёт старые данные за успешно обновлённые.

Дополнение проверено в браузере на локальной production-сборке: две реальные
готовые версии с полными 64-символьными хешами, актуальная и устаревшая версии,
переключение на сцену без рендеров, загрузка, сбой API и восстановление без
переоткрытия окна. По логам API запросов нет до открытия и после закрытия окна;
на ширине 1280 px горизонтального переполнения нет. Повторно прошли 98 тестов
продукта, проверка TypeScript, 22 теста product roadmap и сборка Web.

## Совместимость и выпуск

Миграция 4 обратно совместима со схемой 3: добавляет nullable
`scene_renders.content_hash`, сохраняет старые строки с `NULL` и допускает прежние
SQL-запросы API/worker. Существующие истории не переписываются; при откате кода
колонку удалять не нужно. `ALTER TABLE` требует блокировку, поэтому отсутствие
изменения данных не означает отсутствия времени ожидания. У старых материалов
без хешей байты читаются при построении версии, и их хеши сохраняются в снимке
рендера. Старые задания без цепочки
зависимостей не признаются актуальными: первый запрос создаёт проверяемую версию.
Ошибка чтения старого материала возвращается явно, без вымышленного хеша.

CI проверяет миграцию на отдельной PostgreSQL: новая база, параллельный/повторный
запуск, обновление со схемы 3, записи старого формата и откат при ошибке. Команда
`yarn db:migrate` использует собранный Node.js runner и только `DATABASE_URL`, без
API-ключей. В CD она запускается перед API и worker; ошибка останавливает выпуск
сервиса. Подробности и настройки — в [руководстве CI/CD](deploy-railway.md#database-migrations-in-cicd).

Первый выпуск F05.1 требует порядка: миграция в pre-deploy worker → обновление
всех worker и остановка старых экземпляров → API → Web. Нельзя оставлять старые
worker обрабатывать задания нового API: они не сохраняют хеш результата.
Pre-deploy не задаёт порядок между сервисами автоматически. 28 августа 2026 года
первый выпуск в production выполнен именно в этом порядке: проверенный в CI коммит
`dc4871a62aee305f0ee7e64de7e59f067270e79d` отдельно развёрнут в worker, API и Web;
старые экземпляры worker остановлены до запуска нового API. Результаты и идентификаторы
выпуска записаны в [руководстве CI/CD](deploy-railway.md#verified-first-rollout-2026-08-28).

Версии экспорта сохраняются до удаления сцены. Политика хранения архивных оригиналов
остаётся в F10.1; F05.1 не добавляет undo или восстановление удалённых материалов.
Объектные ключи внутри приложения неизменяемы: замена содержимого создаёт новый
объект, а не перезаписывает старый путь.

## Связанные задачи product roadmap

F04 добавит мастер истории и его зависимости от версий сцен. F07.3 добавит микс,
привязанный к точному таймлайну. Проверка качества и подтверждения относятся к
F05.2/F08.1.1/F15.1, а не к статусу `current`. Эти возможности не объявлены
реализованными. Native Mobile и MCP сохраняют milestones P1/P2.
